04 — Bugs, Errors & Issues
🔴
QIIB payment gateway non-functional
lib/qiib.ts — createQiibSession(), getQiibPaymentStatus(), and verifyQiibWebhookSignature() all contain TODO stubs. Qatar users cannot pay. Graceful degradation in place (shows "contact support@hayyamed.pro"). Revenue blocker.
Fix: Implement once QIIB merchant services provides API documentation + sandbox credentials.
🔴
QIIB webhook signature verification always returns false
lib/qiib.ts:167 — safe default (no false payments processed) but must be implemented before QIIB goes live.
Fix: HMAC-SHA256 comparison once QIIB webhook secret format is confirmed.
🟡
No Suspense boundaries on data-heavy pages
Dashboard settings fetches 7+ parallel DB queries synchronously. Users see a blank page during load instead of progressive skeleton UI.
Fix: Wrap non-critical sections (referral, multi-country wallets, badges) in <Suspense fallback={<Skeleton />}>.
🟡
No design token system — all colors hardcoded in Tailwind
All 153 components use arbitrary Tailwind values like bg-[#1a56a0]. A brand color change requires mass find-replace across the entire codebase.
Fix: Define tokens in tailwind.config.ts theme, replace arbitrary values with semantic classes (bg-primary, text-muted).
🟡
No lazy-loading of heavy modal components
Modals (e.g., AddActivityButton.tsx) are imported at page level and included in the initial JS bundle, increasing first-load time.
Fix: const Modal = dynamic(() => import("./Modal"), { ssr: false })
🔵
General API endpoints have no rate limit
Middleware caps /api/auth/*, /api/ai/*, and webhooks but not general CRUD endpoints. High-frequency replay attacks on other endpoints are uncapped.
Fix: Add a general tier (e.g., 600 req/min per authenticated user) in middleware.
✅
Sign-out only accessible from Settings — FIXED
Previously, sign-out was buried in the Settings page only. Now: LogOut icon in desktop header (top-right, red on hover) + full sign-out row in mobile drawer footer.
Fixed 2026-06-18 — commit 507b96b

Recommendation: Two-Phase Approach

Phase A — 1–2 Weeks

TWA for Android Play Store

Wrap existing PWA in a Trusted Web Activity. Zero code changes to the web app. Creates immediate Play Store presence.

  • Install @bubblewrap/cli
  • Configure Digital Asset Links JSON on hayyamed.pro
  • Build signed APK, upload to Play Store
  • Cost: Google Play one-time $25 fee
Phase B — 6–8 Weeks

React Native / Expo (iOS + Android)

Full native app. Shared business logic, API calls, Zod schemas, types. New: React Native screens, offline sync, biometrics, APNs.

  • Expo SDK with expo-router (file-based navigation)
  • Supabase JS SDK + Bearer token auth (no cookies)
  • expo-secure-store (iOS Keychain / Android Keystore)
  • expo-local-authentication (Face ID, Touch ID)
  • EAS Build + EAS Submit for OTA updates + store submission
  • Web checkout only — Apple reader app exemption
Apple App Store — Subscription rule: Hayya Med Pro qualifies as a reader app (displays CME records and licenses the professional creates elsewhere). Apple’s reader app exemption means in-app purchases are NOT required. All subscriptions remain on web checkout, avoiding the 30% Apple commission entirely.

09 — Subscription & Apple Pay Strategy

Current Payment Architecture

Paddle Active

Global payments — credit/debit cards, PayPal. Webhook-verified subscription lifecycle. Pro + 4 Employer tiers × monthly/annual. PCI DSS Level 1.

QIIB Bank (Qatar) Skeleton

Qatar-specific gateway: Visa/MC/NAPS/QPay/SADAD. Table, routes, types built. API calls pending merchant docs. Graceful degradation active.

Apple Pay Integration Plan

ContextApproachRiskTimeline
Web (Safari / Chrome) Paddle natively shows Apple Pay in its checkout overlay on Safari and Chrome with saved Apple Pay cards. No code changes — only Paddle dashboard domain verification needed. Low 15 minutes (domain registration only)
iOS Native App (Phase B) Redirect to web checkout (Paddle). Safari web view shows Apple Pay natively. No in-app purchase required (reader app exemption). Low When React Native app ships
Android App (Phase B) Same as iOS — Paddle web checkout supports Google Pay on Android browsers automatically. Low When React Native app ships
To activate Apple Pay today: In Paddle dashboard → Checkout settings → Apple Pay → Add domain → hayyamed.pro. Paddle handles the Apple Pay JS, merchant certificates, and token exchange. Zero backend code changes needed.

Subscription Flow (All Platforms)

User clicks Upgrade
↓ UpgradeButton.tsx calls /api/payment/qiib/create (QAR) or opens Paddle checkout (USD)
↓ User completes payment (Apple Pay / card / QPay)
↓ Webhook received and verified (Paddle signature or QIIB HMAC)
↓ subscriptions row updated in DB
↓ getUserPlan() returns new plan on next request
↓ All feature gates and PDF walls unlock immediately

Payment Security Checklist

  • Paddle PCI DSS Level 1 — no card data touches our servers
  • Paddle webhook signature verified via paddle.webhooks.unmarshal()
  • Subscription status enforced server-side in getUserPlan() — never client-only
  • Free tier limits enforced in API routes, not just UI
  • QIIB webhook HMAC: implement before enabling QIIB live
  • Apple Pay: register hayyamed.pro in Paddle dashboard (15 min task)
  • 4 QIIB secrets pre-named in GCP Secret Manager schema — add values when creds arrive
